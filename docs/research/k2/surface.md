# k2 vetting: stage 3 "surface" (mesh to CAD surface) plus STEP/3MF export

Date 2026-10-22. Targets: `vernon-nodes-surface`, `vernon-io` (STEP, 3MF). Supporting changes that these two need in `vernon-core` are listed separately.
Input: 70 condensed k2 claims (33 from chunk c07, 37 from chunk c08). k2 never saw Vernon's code; claims are treated as untrusted data.
Checked against: `CLEAN_ROOM.md`, `vernon-core` (`geometry.rs`, `report.rs`), `vernon-graph` (`node.rs`, `param.rs`, `data.rs`), `docs/specs/reverse-engineering-surfacing.md`, `docs/specs/rhino8-mesh-tools.md`, `docs/specs/slicing-printing.md` (3MF part). Crate facts come from `cargo info` plus the open-source crate manifests in the local cargo cache (build scripts, dependencies); no proprietary files were touched. Formulas were re-derived by hand.
Docs under `docs/research` may name vendors; none of the verdicts below puts a vendor name into a UI string.

## 1. Summary

1. Tally: 3 ACCEPT, 41 ADAPT, 26 REJECT (70 claims). Almost all k2 code is OCCT behind a C++ shim. That route is rejected as a whole: C++ and LGPL-2.1 dependency, FFI undefined-behaviour surface, and five vendor-named placeholder nodes that would break CLEAN_ROOM.
2. k2's maths is wrong in the places that matter, so none of its subdivision, orientation or continuity code may be ported. Confirmed: its vertex rule scales a constant mesh by 1.5, its edge point is not Catmull-Clark, its single-quad expectation (11 vertices) should be 9, its cube test is wound inward, and its continuity integer maps to the wrong OCCT enum. The summariser's note on the 1e-7 sewing tolerance is also wrong for f64 (see section 3).
3. The good ideas survive as Report-gated checks in pure Rust: watertight/boundary-edge/orientation metrics, a measured fit deviation checked against the tolerance, deviation gated on p95 rather than max, and tests that really re-read the written STEP and 3MF.
4. Dependencies: Phase 1 needs none. The only credible pure-Rust STEP route for NURBS is `truck-stepio` (Apache-2.0, `build = false`, writes `SI_UNIT(.MILLI.,.METRE.)`): spike it behind a cargo feature. 3MF stays hand-rolled (`vernon-io` already has it on `miniz_oxide`); k2's `threemf` 0.5 / MIT data is stale (now 0.8.1, 0BSD) and the crate is redundant.
5. Biggest design gap: `Geometry` has no NURBS. Add `vernon-core::nurbs` (curve, surface, validation) and carry patch sets as `Data::Json` (`nurbs_patch_set`) plus a tessellated preview `Geometry` (prim attrib `patch_id`), exactly as spec section 4 says; no new `DataKind`. STEP goes out as `Data::File`.

Legal verification (general area only, 6 web searches in total: 4 in the original run plus 2 repeat checks in the resumed run, one over the cap of 5; the repeats re-confirmed the two facts below): k2 cites no case names, courts or years anywhere in this range, so there is nothing to verify at case level. Licence facts checked: OCCT 6.7.0 and later (released Dec 2013) is LGPL-2.1 plus the "Open CASCADE Exception 1.0"; 6.6.0 and earlier used the older OCCT public licence (VERIFIED via https://fedoraproject.org/wiki/Licensing/Open_CASCADE_Technology_Public_License and the Debian copyright files for opencascade 7.x, e.g. https://tracker.debian.org/media/packages/o/opencascade/copyright-7.9.2dfsg-4; the vendor's own licence page did not come up in search, so read LICENSE_LGPL_21.txt and OCCT_LGPL_EXCEPTION.txt in the source tree before any redistribution). QuadriFlow is a real paper (Huang, Zhou, Niessner, Shewchuk, Guibas, Computer Graphics Forum vol. 37 issue 5, 2018, pp. 147-160, presented at SGP 2018; https://diglib.eg.org/handle/10.1111/cgf13498) (VERIFIED); its README says MIT but also carries an "All Rights Reserved" line and lists LGPL sparse-Cholesky code with a BUILD_FREE_LICENSE option, so its licence is ambiguous (https://projects.blender.org/archive/blender-archive/src/commit/2055ef107a7cb4e5aeeffb5ccc8a2908a59cd7d0/extern/quadriflow/README.md): read its LICENSE file before any use. Instant Meshes licence and command-line flags: UNVERIFIED (search returned nothing authoritative). k2's LGPL-section-6 compliance conclusion (dynamic linking plus shipped source tarball is enough): UNVERIFIED, only informal discussion found; needs counsel, and it becomes moot if OCCT is not used.

## 3. Bugs and hazards (k2's code and claims, plus adoption risks)

H1. Subdivision (S21-S24): face point right; edge point and vertex rule wrong; weights (1 + 2 + 2 + 1) / 4 = 1.5; unit-square result must be 9 vertices and 4 quads (Euler V-E+F = 9-12+4 = 1). My hand checks of the correct rule, on the cube [-1,1]^3 corner (1,1,1) with n = 3: F = (1/3,1/3,1/3), R = (2/3,2/3,2/3), so (F + 2R + 0P)/3 = (5/9, 5/9, 5/9) after one step; limit position (n^2 v + 4 sum e + sum f) / (n(n+5)) = (9v + 4 sum e + sum f) / 24 = (9 + 4 - 1) / 24 = 0.5 per axis, so (0.5, 0.5, 0.5) (e = edge-neighbour vertices, f = diagonal vertices of the incident faces). Use these as golden values; the cube extent must be stated in the test.
H2. Sewing/weld tolerance (S03): the note that 1e-7 mm "is close to double-precision noise at 100 mm" is wrong for f64 (ulp near 100 is about 1.4e-14 mm). It is below the f32 ulp, which is 7.6e-6 mm at 100 mm and 2.4e-4 mm at 2.5 m. Meshes read from STL are f32: vertices that a mesher computed separately for each triangle, or that were rounded after a transform, can differ by about one f32 ulp even though they are meant to coincide (copies written from one shared value stay bit-equal). Vernon rule: weld tolerance = max(param, about 1.2e-7 x max abs coordinate). Spec default weld 1e-6 mm is fine only for f64 data.
H3. Orientation (S04, S10): k2's cube is wound inward (triangle [0,1,2] on the -Z face has normal +Z; confirmed by cross product). A closed inward solid has negative volume, so k2's own `volume > 0` gate rejects k2's own test. A TopAbs flag does not change winding.
H4. `volume > 0` gate (S09): wrong for open surfaces; `Metric::passes` is inclusive so a zero-limit volume metric passes at 0.
H5. Quads (S15): k2's `is_all_quads` is always false with fixed `[u32;3]`; Vernon does not have that limit. Splitting quads into (q0,q1,q2),(q0,q2,q3) is valid for convex quads only. `Geometry::triangles()` is a fan from vertex 0, which is wrong for concave n-gons, and the `vernon-io` writers fan-triangulate too: a dart-shaped quad (from a CC level or a remesher) exports with a flipped or overlapping triangle. Fix in IO-4.
H6. Closest point (S16): static OnceLock built from the first mesh makes later queries wrong and the result order-dependent; nearest vertex is not distance to the surface; f32 loses 4.9e-4 mm at 4.5 m; k2's kiddo calls do not match the current API (kiddo is now 6.3.0).
H7. Fingerprint caches (S13, S44): lossy keys return stale geometry. Silent default for missing `tolerance` (S34) hides wiring errors.
H8. Ramp (S38): k2 normalises by mesh max (colour no longer means pass/fail) and its implemented ramp reportedly gives blue at 0.5 and green at 1 (the intended formula is right). Black as "no colour" collides with legitimate dark colours.
H9. Continuity enum (S49): integer-to-enum cast hits C1 for input 2. Also "G2 from QuasiUniformTangents" is unverified.
H10. STEP/3MF (S57-S64): k2's STEP "precision" is a no-op; STEP does not need triangulation; BRep to 3MF path silently writes an empty model; tests rely on missing directories and a filename with a space; `tri_buf` typed as f64 for indices; 3MF is not "binary STL-style".
H11. Licence incoherence (S14, S66): "only uses OCCT, does not redistribute" versus "installer ships OCCT"; "libloading at runtime" versus a link-time `extern "C"` block; shim BSD-3 versus Apache-2.0; `vdb_shim` / `oc_shim` / `openvascade` naming slips. k2's compliance conclusions are asserted without sources (UNVERIFIED).
H12. FFI (S11, S12, S54): leaked handles by design, `new[]` freed with `libc::free`, placement-new into uninitialised slots, exceptions other than Standard_Failure crossing the C boundary. All are removed by not using FFI.
H13. Vendor SDK adapters (S32): invented-looking API names and unsourced class names (for example `GeomConvert_SurfaceToBSplineSurface` as a class); do not cite them even in docs as fact.
H14. Overclaiming timings (S08, S19): none benchmarked; "10M triangles in under 6 s" must not appear in any test or spec.
H15. Workspace MSRV: `Cargo.toml` says `rust-version = 1.80`, installed toolchain is rustc 1.99.1, but candidate crates need much newer compilers (kiddo 1.89, nalgebra 1.89, bvh 1.90, image 1.88, rstar 1.85). Adopting any of them means raising the workspace MSRV on purpose.
H16. `truck-stepio` risks (adoption, not k2): 0.3.0 pins `ruststep` 0.4 and `chrono`; its header text is hard-coded ("Shape Data from Truck", whether it can be overridden is unchecked, so confirm no vendor-looking text leaks into user files); boolean/trim robustness of the truck modeller is not what we need and is not used; memory use for faceting millions of faces is unmeasured. Spike before committing.
H17. Quadriflow/Instant Meshes (S29): QuadriFlow licence text is ambiguous (MIT line plus "All Rights Reserved" plus optional LGPL part), Instant Meshes licence UNVERIFIED. Running them as separate processes avoids linking but not the need to read LICENSE before distributing a binary.
H18. `Geometry::validate()` does not reject NaN or infinite coordinates or degenerate prims; STEP/3MF writers must (IO-1).
H19. Attribute-name clash inside Vernon (not k2): `geometry.rs` documents the signed deviation point attribute as `dist` (Float, mm), but `docs/specs/reverse-engineering-surfacing.md` section 4 names it `dev_mm`. Decision for this vetting: use `dist` everywhere (it is the cross-node convention in code), and edit the spec row for `surface.deviation_check` to match. Test: the registry lint or a doc test asserts the attribute written by `deviation_check` is exactly `dist`.
H20. Test portability (adoption risk, development host is Windows): export tests must build paths with `Path::join` under `CARGO_TARGET_TMPDIR`, never hard-code `\` or `/`, and the STEP header and entity names must stay ASCII.
